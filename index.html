這是 Anthropic 官方《Prompting Claude Fable 5》指南的新手解讀版：每一節先講「官方在說什麼」、再用白話解釋「為什麼」、附上可以直接複製貼上的英文指令（官方原文），最後連到案例庫裡的實際例子。

一句話總綱：把 Fable 5 當成「能獨立工作好幾小時的同事」，而不是「一問一答的聊天機器人」——你的工作從下指令，變成定義目標、給足背景、設好界線。

① 心理準備：它的「一回合」變得很長

官方說難題在高 effort 下單次回應可能跑好幾分鐘，自主任務可以連跑數小時——這是團隊適應 Fable 5 時最大的衝擊。

白話以前的模型像即時通訊，Fable 5 像交辦工作給同事：交出去之後去做別的事，回來驗收。如果你的程式會呼叫它，記得調高 timeout、改用串流。如果它在簡單問題上想太久，貼這段：

When you have enough information to act, act. Do not re-derive facts already established in the conversation, re-litigate a decision the user has already made, or narrate options you will not pursue in user-facing messages. If you are weighing a choice, give a recommendation, not an exhaustive survey.

實例：Mollick 的 Concord 案例——一次跑 9.5 小時。

② Effort：最重要的一顆旋鈕

官方說effort 是智力、速度、成本三者取捨的主控制。預設用 high；最難的任務用 xhigh；例行工作用 medium/low——而且 Fable 5 的低檔常常贏過舊模型的最高檔。

檔位什麼時候用
xhigh最難、最在乎品質的任務（複雜工程、深度分析）
high（預設）大多數任務從這裡開始
medium / low例行工作、想要快一點的互動節奏

白話嫌它慢就降檔，嫌它淺就升檔。高檔位時它可能順手「大掃除」（重構你沒叫它動的代碼），用這段擋住：

Don't add features, refactor, or introduce abstractions beyond what the task requires. A bug fix doesn't need surrounding cleanup and a one-shot operation usually doesn't need a helper. Don't design for hypothetical future requirements: do the simplest thing that works well. Don't add error handling, fallbacks, or validation for scenarios that cannot happen. Trust internal code and framework guarantees. Only validate at system boundaries (user input, external APIs).

實例：Pokémon 複刻用 extra high 推理 1 小時；Minecraft 用 high 20 分鐘。

③ 指令跟隨變強：一句話就夠，不用列清單

官方說以前要逐條列舉的行為規範，現在一句簡短指令就能管住。例如嫌它話太多，不用列「不要 A、不要 B、不要 C」，一段就夠：

Lead with the outcome. Your first sentence after finishing should answer "what happened" or "what did you find": the thing the user would ask for if they said "just give me the TLDR." Supporting detail and reasoning come after. Being readable and being concise are different things, and readability matters more.

白話把它當聰明人對待：講原則，不用講 SOP。連「什麼時候該停下來問我」也只要一句：

Pause for the user only when the work genuinely requires them: a destructive or irreversible action, a real scope change, or input that only they can provide. If you hit one of these, ask and end the turn, rather than ending on a promise.

④ 長跑必加：報告要有證據

官方說長時間自主任務時，要求它把每個進度宣稱對照實際的工具結果。Anthropic 內部測試中，這段指令幾乎消滅了「謊報進度」。

白話等於跟同事說「報告要附截圖」。任何超過半小時的自動化任務都建議加：

Before reporting progress, audit each claim against a tool result from this session. Only report work you can point to evidence for; if something is not yet verified, say so explicitly. Report outcomes faithfully: if tests fail, say so with the output; if a step was skipped, say that; when something is done and verified, state it plainly without hedging.

實例：機械錶視覺驗證迴圈——「用視覺逐零件檢查到 100% 滿意」就是證據導向的設計。

⑤ 講清楚界線：它偶爾會「順手多做」

官方說Fable 5 偶爾會做你沒要求的事（沒人叫它寫 email 它先擬好一封、自己開 git 備份分支）。要明確定義該做與不該做：

When the user is describing a problem, asking a question, or thinking out loud rather than requesting a change, the deliverable is your assessment. Report your findings and stop. Don't apply a fix until they ask for one. Before running a command that changes system state (restarts, deletes, config edits), check that the evidence actually supports that specific action.

白話「我在抱怨」≠「我要你修」。這段就是教它分辨這兩件事。

⑥ 給原因，不要只給請求

官方說Fable 5 理解請求背後的意圖時表現更好——背景讓它把任務連到相關資訊，而不是自己猜。

白話新手最容易上手、效果最大的一招。背下這個句型：

I'm working on [the larger task] for [who it's for]. They need [what the output enables]. With that in mind: [request].

中文版：「我在為〔誰〕做〔什麼大事〕，他們需要〔這個產出拿來做什麼〕。基於這個背景：〔你的請求〕。」

⑦ 建一個記憶系統（一個 Markdown 檔就夠）

官方說Fable 5 特別擅長記錄並引用過往教訓。給它一個寫筆記的地方，簡單到一個 .md 檔即可：

Store one lesson per file with a one-line summary at the top. Record corrections and confirmed approaches alike, including why they mattered. Don't save what the repo or chat history already records; update an existing note rather than creating a duplicate; delete notes that turn out to be wrong.

白話讓它越用越懂你。第一次啟用時可以叫它回顧歷史對話自己整理：

Reflect on the previous sessions we've had together. Use subagents to identify core themes and lessons, and store them in [X]. Make sure you know to reference [X] for future use.

⑧ 兩個偶發小毛病與解法

毛病一長 session 深處，它偶爾說「我接下來會跑 X」然後就停了。回一句「continue」即可；自動化管線則預先貼這段：

You are operating autonomously. The user is not watching in real time and cannot answer questions mid-task. For reversible actions that follow from the original request, proceed without asking. Before ending your turn, check your last paragraph. If it is a plan, a question, a list of next steps, or a promise about work you have not done ("I'll…"), do that work now with tool calls. End your turn only when the task is complete or you are blocked on input only the user can provide.

毛病二超長 session 它偶爾會主動提議「開新對話吧」。如果你的工具會顯示剩餘 token 數給模型看，加一句安撫：

You have ample context remaining. Do not stop, summarize, or suggest a new session on account of context limits. Continue the work.

⑨ 進階：並行子代理與驗證

官方說Fable 5 比以前更敢派出並行子代理。建議多用、明確說清楚何時該委派、並讓主代理「邊等邊做」而非乾等：

Delegate independent subtasks to subagents and keep working while they run. Intervene if a subagent goes off track or is missing relevant context.

白話驗證工作交給「獨立的檢查員」勝過讓它自己檢查自己——這正是案例庫裡 Lance Martin 實驗的結論（verifier 子代理 vs self-critique）。長跑任務加：

Establish a method for checking your own work at an interval of [X] as you build. Run this every [X interval], verifying your work with subagents against the specification.

實例：等時圈地圖——自主派子代理查 2,200+ 航班、互相驗證。

⑩ 給老用戶的三個提醒

1. 出更難的題。官方原話：只拿簡單任務測它，會低估它的能力範圍。挑一個比你以前敢交給 AI 更難的任務，讓它自己釐清範圍、提問、執行。

2. 舊的 prompt 和 skill 要瘦身。為舊模型寫的鉅細靡遺指令，對 Fable 5 反而可能「降低」輸出品質——先刪掉試試預設表現。

3. 別叫它「展示思考過程」。要求它複述內部推理會觸發安全分類器（reasoning_extraction），導致回應被降級到 Opus 4.8。需要看推理就讀 API 的 thinking blocks，別用 prompt 要。

⚠️ 另外注意：Fable 5 不做攻擊性資安和生物相關任務（會直接拒絕）；正當的資安防禦工作偶爾也會誤觸，官方建議設定自動 fallback 到 Opus 4.8。
